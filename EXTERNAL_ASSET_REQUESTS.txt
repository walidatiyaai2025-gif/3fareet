3FAREET — EXTERNAL ASSET REQUEST POLICY & ACTIVE REQUESTS
=========================================================

PURPOSE
-------
This root-level file is the mandatory creation/handoff ledger for any project item that cannot be completed safely and truthfully by repository code alone (for example: final authored 3D art, hand-authored textures, audio recordings, licensed fonts, owner-approved reference art, or other external creative/source material).

`docs/MISSED_ASSETS.md` remains the detailed inventory/status registry. THIS root file is the mandatory copy-ready creation brief whenever an inventory item needs external authored source material. If the two documents disagree about whether programming can solve a problem, programming/automation remains an engineering responsibility and must not be pushed into this ledger as an art request.

POLICY — MANDATORY FOR EVERY PROGRAMMER / AI AGENT
-------------------------------------------------
1. Programming first. Close code, tests, build gates, import/staging pipelines, runtime binding, diagnostics and validation before asking the owner for external assets.
2. Do NOT silently substitute a primitive, generated placeholder, procedural mesh, preview asset or review candidate for missing production art.
3. A placeholder/review asset may exist only when clearly classified as DEBUG / PREVIEW / REFINEMENT / REVIEW and it must never satisfy a production or P1 visual gate.
4. The moment an implementation is blocked by an external asset that the current coding/AI toolchain cannot legitimately create as final production material, add or update an entry in THIS file in the same PR/branch.
5. Every request entry MUST contain: ID, status, blocked task/issue, asset name, purpose, tool, helper script/workflow, exact output path/format, creation prompt/brief, technical constraints, acceptance criteria, provenance/license requirement, and integration owner notes.
6. Prompts must be ready to copy/paste into the named tool or give directly to a human artist. Do not write vague requests such as "make a better car".
7. If Blender is the recommended tool, specify Blender version family, scale/axis, LOD expectations, materials/textures, naming, export format and destination.
8. If a helper script can be written by the programming team (validation, export checks, naming checks, texture audit, packaging, deterministic import), write that script in the repo. Do NOT use a script to pretend procedural/generated art is externally authored production art.
9. Never mark an external request DONE until the delivered source is committed (when licensing permits), its provenance is recorded, the runtime uses it, and the relevant acceptance gate is satisfied.
10. Keep this file append/update friendly. Do not delete historical request entries; mark them DELIVERED / SUPERSEDED and reference the replacement.
11. Production source must have a clear license/ownership statement. Unknown-license marketplace/downloaded assets are not acceptable.
12. Until the owner explicitly says to resume polish/visual review, engineering work should prioritize missing programming, automation, deterministic pipelines, tests, validation and evidence tooling.

STATUS VALUES
-------------
OPEN            = owner/artist/source material still required.
IN PROGRESS     = external creation is underway; programming may continue around it.
DELIVERED       = source received, but runtime/acceptance may still be pending.
ACCEPTED        = source + runtime + relevant owner/gate acceptance completed.
SUPERSEDED      = replaced by another request; keep the record.
